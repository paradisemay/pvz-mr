# Architecture guidelines

## Принципы
1. **Логика отдельно от Unity.** Правила игры (что такое заказ, правильная ли коробка, сколько очков) живут в `Pvz.Core`
   без ссылок на `UnityEngine` и покрываются EditMode-тестами. MonoBehaviour-ы — тонкие адаптеры.
2. **Зависимости в одну сторону:** `Editor → Runtime → Core`. Core ничего не знает о сцене.
3. **События вместо прямых вызовов между фичами.** Источник события — Core (`PickupDesk.OrderCompleted`,
   `PickupDesk.WrongHandover`, ...). UI, звук, клиенты подписываются; `ShiftDirector` — единственный, кто их связывает.
4. **Сцена собирается кодом.** `PvzSceneBuilder.BuildAll` (с `PvzPrefabBuilder` и `PvzAssetFactory`) создаёт префабы,
   материалы, QR-текстуры, пресеты сложности и сцену `Game.unity`. Ручные правки допустимы, но всё, что нужно для
   воспроизводимости, — в билдере.
5. **Сканирование отделено от Core.** Игровая логика получает `BoxId`, а не «кадр камеры»: `HandScanner` сообщает
   `BoxScanned(QrBox)` (raycast по `QrBox`), директор передаёт `Shift.Scan(id)`. Распознавание камерой позже
   подставляется на месте `HandScanner`, не трогая Core.
6. **Нет синглтонов и `FindObjectOfType` в рантайме.** Ссылки — через сериализованные поля, которые проставляет билдер.
7. **Детерминизм для тестов.** Случайность — через `IRandomSource`, время — параметром (`now`), а не `Time.time` внутри Core.

## Решения, принятые по итогам ревью T003
- **Правила смены — в Core (`Shift`)**: какой заказ следующий, когда смена окончена, какие коробки из зоны
  выдачи отдать пришедшему клиенту. `ShiftDirector` — только композиция, темп (корутины) и проброс ввода.
- **Все тексты и звуки — в `ShiftPresenter`**, который подписан на события Core. Новая фича = новое событие
  в Core + реакция в презентере, а не ещё один `switch` в директоре.
- **Раскладка коробок — в `ShiftSettings`** (id, номер заказа, стартовая позиция) — единый источник правды для
  билдера сцены и для логики.
- **Билдер не затирает работу художника**: существующие материалы не перезаписываются. Когда появятся
  настоящие модели — художник делает их отдельными префабами в `Art/`, а билдер переводится в режим
  «проверить и связать» (тест `SceneIntegrityTests` ловит неназначенные ссылки после ручных правок).
- **На шлеме всё игровое — под `Play Area`**, который выравнивается по позиции и взгляду игрока; симулятор и
  мок-комната помечены `EditorOnly` и не попадают в сборку.

## Решения T004–T006
- Расписание поставки, приёмка, пакет и терпение клиентов — правила Core (`SupplyPlan`, `Shift.Tick`,
  `ServiceSession.AwaitingBag`); директор только спавнит объекты и пробрасывает ввод.
- Каждая новая реакция игрока = событие Core (`BoxReceived`, `BagRequested`, `CustomerHurried`, `OrderAbandoned`)
  + обработчик в `ShiftPresenter`.
- Пресет сложности — отдельный `ShiftSettings`; раскладка склада в пресетах одинакова (проверяется тестом).
- Отложено осознанно: явный список заказов со статусами (сделан в T019), обобщённый `ExtraRequest`,
  `DifficultyPreset` поверх одной раскладки, `GameFlow` для фаз «меню → смена → итоги».

## Решения T007–T011
- Очередь клиентов — правило Core: упорядоченная линия зарезервированных заказов в `Shift` (`TryEnqueue` с длиной
  очереди, `OpenNext`, `LeaveQueue`); директор хранит только «какой клиент на каком месте». Список заказов со
  статусами — T019 (журнал `OrderBook`).
- Разрешение `USE_SCENE`: `ARPlaneManager` сохранён в сцене выключенным, `ScenePermissionGate` включает его после согласия.
- Рекорды: правило в Core (`BestScores` → `RecordResult`), хранилище — интерфейс `IScoreStore`
  (`PlayerPrefsScoreStore` в Runtime, `MemoryScoreStore` в тестах); ключ — стабильный id пресета (имя ассета).
- Полоска терпения: `Shift.PatienceRemaining` → `ShiftPresenter.UpdatePatience` → `PatienceBar`; цвета привязаны к `Shift.HurryFraction`.
- Подсказки первого заказа — шаги «только вперёд» в `ShiftPresenter` (`ShiftSettings.showTutorial`).

## Решения T013 (возвраты)
- Очередь состоит из `Visit` с явным `VisitKind` (`Pickup` / `Return`); новый вид доп. запроса — новый `VisitKind`,
  а резерв склада идёт только через `Visit.ReservedOrderNumber`, без проверок «а не возврат ли это».
- `PickupDesk` обслуживает одного клиента: заказ **или** возврат (`HasCustomer`); `OpenReturn` / `ReturnAccepted`.
  Единый `ActiveVisit` на стойке — когда видов визита станет больше двух (или появятся несколько стоек);
  список заказов со статусами сделан в T019 как журнал смены поверх стойки.
- Проданная коробка может вернуться только возвратом: её id запоминается в `Shift` и отклоняется в поставках.
  Скан коробки активного возврата проверяется раньше приёмки поставки.
- Директор не ветвится по виду визита: коробку возврата кладёт обработчик `Desk.ReturnOpened` на
  `HandoverZone.ReturnSpot` (рядом с зоной, не внутри — не задевает подготовленные коробки). Без префаба коробки
  возвраты выключаются с ошибкой в логе — бесплатных очков «по скану ничего» нет.

## Решения T014 (случайные события)
- Правило: **свойство**, меняющее то, *как* идёт выдача заказа, живёт на неизменяемом `Order` (пакет, срочность,
  «забыл номер»); **другой ход обслуживания** на стойке — новый `VisitKind`. Срочный и забывчивый клиент проходят
  обычный путь `OpenOrder → Scan → Handover`, поэтому это свойства заказа.
- Свойства бросает `OrderGenerator` через `IRandomSource`, только при шансе > 0 (старые последовательности заказов
  не меняются). Подсказка «••NN» однозначна среди всех заказов смены: `Shift` передаёт генератору склад, ожидающую
  и плановую поставку.
- Терпение конкретного заказа — `Shift.PatienceFor` (коэффициент срочности проверяется: (0, 1]); бонус — `ShiftStats`.
- Формат номера («••81») и реплики — `ShiftPresenter.SpokenNumber` / `GreetingFor`. Сканер намеренно показывает
  полный номер коробки: это способ найти заказ забывчивого клиента.

## Решения T015 (таймер смены)
- Время — отдельный тип Core `ShiftClock` (лимит, старт, `TimeLeft(now)`, `TryRunOut(now)` — ровно один раз);
  последствия решает `Shift`: в `Tick(now)` (как и терпение) при истечении времени очередь, кроме стоящего у стойки,
  уходит, затем `TimeUp(sentAway)` — после фиксации состояния. При вышедшем времени `CanEnqueue` и `IsDeliveryDue`
  ложны, а `IsOver` = «у стойки никого»; необслуженные заказы остаются на складе.
- Директор только уводит клиентов из `sentAway` и не доводит до стойки того, чей визит уже снят (`IsStillQueued`).
- Формат часов — `ShiftPresenter.ClockText`; строка табло обновляется раз в секунду (`UpdateClock`).
- Длительность — `ShiftSettings.shiftDurationSeconds`; параметры пресетов передаются билдером явно, без значений по умолчанию.

## Решения T016 (похожие заказы)
- Правила о номере как его читает игрок — в `OrderNumbers` (Core): `LookAlike` (одна цифра другая или соседние
  переставлены, длина ≥ 3) и подсказка забывчивого клиента (`HintOf`, `CanHint`, `SameHint`, перенесены из `Order`).
  Какие заказы есть в смене, решают `OrderGenerator` / `Shift`.
- «Похож» — флаг на исходе (`ScanOutcome` / `HandoverOutcome.LooksLikeTheWantedOrder`), а не новый статус:
  это всё та же чужая коробка, счётчики (`WrongScans`, штраф за выдачу) и подсказки не меняются. Для забывчивого
  клиента флаг не ставится — иначе сканер сказал бы больше, чем клиент.
- Похожая пара — данные склада и поставки (2781 на складе, 2718 в поставке), а не генерация в Core: коробки —
  объекты сцены с фиксированными id. Пару и различие окончаний номеров для всех пресетов охраняют Editor-тесты.
- Тексты сканера — `ShiftPresenter.ScanResultText`; скриншоты берут текст оттуда же.

## Решения T017 (сохранение расположения склада)
- Раскладка — не часть смены: её ведёт отдельный компонент `WarehouseLayoutKeeper` (собирается билдером сцены),
  директор о ней не знает. Keeper восстанавливает коробки в `Start` (до меню), запоминает место по событию
  `QrBox.Placed` (коробку отпустили, и она успокоилась) и сразу сохраняет; ещё раз — на паузе приложения.
- Правило «зона выдачи — не место на складе» применяется в момент постановки (по сфере вокруг коробки, а не по
  центру), поэтому коробка, заранее положенная в зону и выданная, сохраняет своё прежнее место на складе.
- При восстановлении место проверяется на свободу (`QrBox.IsSpotFree`, коробки по очереди): занятое — коробка
  остаётся на месте по умолчанию; физика никого не расталкивает.
- Core: `BoxPlacement` (правдоподобие — правило валидности данных, не настройка, поэтому не в `ShiftSettings`),
  `WarehouseLayout` (формат «v1»: координаты относительно корня коробок игровой зоны, которая выравнивается по игроку
  в каждой сессии), `ITextStore`/`WarehouseLayoutStore` — по образцу `IScoreStore`/`BestScores`.
- Тесты подменяют хранилище до загрузки сцены (`WarehouseLayoutKeeper.StoreOverride`): настоящие сохранения
  разработчика в тесты не попадают.
- Отложено: привязка к настоящей комнате (пространственные якоря Meta, формат v2); кнопка «сбросить склад» — T020;
  общий тип границ склада для `BoxPlacement` и «потерянной коробки» в `QrBox` — сделано в T025 (`WarehouseBounds`).

## Решения T018 (голос и визуальные эффекты)
- Правило «тексты и звуки — в презентере» уточнено: **решает** (что и когда) `ShiftPresenter`, **исполняют**
  компоненты сцены. `Customer.Say` показывает реплику и озвучивает её (`CustomerVoice`) — текст и голос неразделимы,
  как реплика и пузырь; `HandScanner.Flash` подсвечивает экран; `FeedbackEffects` запускает конфетти.
- `FeedbackEffects` — явная необязательная зависимость презентера (сцена без эффектов работает). `FeedbackAudio`
  и `FeedbackEffects` не объединены: разные места и причины меняться; при следующем выходе (вибрация) — общий объект
  «выходов» презентера.
- Голос — процедурный (`Babble`, только в Play Mode), один буфер и один клип на клиента, без аллокаций на реплику;
  заглушка до записи настоящих голосов. Звук — панорамирование (`spatialBlend = 1`), не HRTF: спатиалайзер Meta не подключён.
- Вспышка экрана — временный `MaterialPropertyBlock` поверх цвета материала, по окончании снимается (работа художника
  над материалом экрана не затирается).
- Счётчики (`LinesSpoken`, `Flashes`, `Celebrations`, `ParticlesAlive`) растут только при реальном действии —
  в пакетном режиме тестов нет ни звука, ни картинки.

## Решения T019 (список заказов со статусами)
- `OrderBook` — журнал всех визитов смены; переходы задаёт и проверяет он сам: `Waiting → AtCounter →
  Served | Abandoned`, `Waiting → Left`; недопустимый переход — исключение. Двигает записи только `Shift`
  (внутренние методы; Core-тесты видят их через `InternalsVisibleTo`).
- «У стойки» ставится по событиям стойки (`OrderOpened` / `ReturnOpened`), на которые `Shift` подписан первым,
  поэтому книга актуальна, когда реагируют презентер и директор; заказ, открытый мимо очереди, в книгу не попадает.
- `Changed` — один раз на изменение и после обновления очереди (уход всей очереди по времени — одно событие).
- Очередь — вид книги (T021): `OrderBook.Line` — открытые визиты в порядке прихода; у `Shift` своей очереди больше нет,
  `QueuedVisits` / `QueuedOrders` / резервы считаются по `Book.Line`. Одна правда о том, кто ждёт; тест согласованности остался.
- Почему список появился раньше «третьего вида визита» из T013: игроку нужно видеть очередь (UI), а не стойке.
  Единый `ActiveVisit` на стойке по-прежнему отложен.
- Текст и порядок строк (стойка → очередь → завершённые, новые сверху) — `ShiftPresenter.OrderListText` с цветами
  палитры табло; панель — часть `CounterBoard` (явная ссылка на панель, скрыта, пока список пуст). После конца смены
  список остаётся рядом с итогами как журнал смены.
## Решения T020 (сброс склада)
- `WarehouseLayoutKeeper.ResetLayout`: места по умолчанию запоминаются в `Awake` (до восстановления), пустая раскладка
  сохраняется сразу. Кнопка — только в стартовом меню (до смены), без подтверждения: для прототипа достаточно.
- Коробка в руке игрока не трогается (рукой и её родителем владеет XRI); `MoveToSavedPlace` никогда не меняет
  родителя коробки — только её место и точку возврата.
- Сначала все коробки встают на места, потом проверяется, не занято ли место чем-то ещё (сканер, пакет): такая коробка
  ставится чуть выше и падает, а не выталкивается физикой.

## Решения T022 (карьера и темы стойки)
- Карьера — не часть смены: `CareerKeeper` (как `WarehouseLayoutKeeper`) владеет `Career`, красит стойку и обслуживает
  кнопку «ТЕМА»; директор только сообщает очки завершённой смены (с весом `ShiftSettings.careerPointsPercent`).
- Core знает id и пороги тем (`CounterTheme`) и проверяет список; названия и цвета — в `CounterThemeCatalog`
  (`ScriptableObject`, один на игру: карьера общая для всех сложностей). Выбор темы сохраняется по id.
- `IScoreStore` — общий целочисленный хранилищем данных игрока; у владельцев свои префиксы (`pvz.best.`, `pvz.career.`).
- Меню рисует `ShiftPresenter.ShowDifficultyMenu` целиком (рекорды и строка карьеры).
- `CounterSkin` — блоки свойств поверх материалов (как вспышка экрана в T018): у первой темы их нет, материалы как есть.

## Решения T026 (пульт отладки на шлеме)
- `PvzRemote` — только в редакторе и в отладочной сборке (`#if UNITY_EDITOR || PVZ_REMOTE`, флаг задаёт
  `PvzBuild.BuildQuestApkDev` через `extraScriptingDefines`, не через настройки проекта). В релизном APK нет ни кода, ни порта.
- Пульт не знает правил: нажимает те же кнопки и делает те же действия, что игрок и автотесты (`ScanDirect`, перенос в зону).
- Сокет — в фоновом потоке, команды — в главном; команда, которую игра не взяла за 30 с (шлем снят), отменяется, а не
  выполняется позже. Порт слушает только `127.0.0.1`, но loopback доступен всем приложениям шлема, поэтому первая
  строка соединения — токен из файлов приложения (через `adb` читается, другим приложениям недоступен).
- Видео «как в шлеме» (комната + игра) — встроенная запись Quest; кадры из игровой камеры (`shot`/`record`) — без комнаты,
  и запись кадров стоит времени кадра (ограничена `MaxRecordedFrames`).
- Отладочная сборка объявляет необязательную поддержку рук, иначе без контроллеров Quest не запускает игру.

## Решения T031 (#74, кнопки на курок)
- Кнопки стойки нажимаются через общую `PressableButton`: курок наводящего луча (XRI отдаёт activate только выбранному
  объекту, поэтому курок читается у интерактора) или касание (poke → select). Хват не нажимает; курок руки, которая что-то
  держит, тоже — так сканер не жмёт кнопки. Конкретные кнопки только подписываются на `Pressed`.

## Решения T033 (#77, компьютер на стойке)
- `PvzComputer` — экраны (меню, настройки, смена, итоги) и группы клавиш в одних и тех же слотах. Существующие кнопки
  (`DifficultyButton`, `RecenterButton`, `ResetWarehouseButton`, `ThemeButton`, `RestartButton`) не переписаны — просто живут
  в группах; новые действия экрана — `ComputerKey`. Компьютер слушает `ShiftDirector.ShiftStarted/ShiftEnded`.
- «Завершить смену» — это истечение времени по просьбе игрока (`Shift.EndNow`): одно поведение конца смены вместо двух.
- Сохранённая сцена показывает экран меню (`Preview`), группы скрываются последними — иначе надписи клавиш в скрытых
  группах не размечаются вне play mode.
